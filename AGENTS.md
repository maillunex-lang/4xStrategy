# Инструкция исполнителю
1. Прочитай этот файл и строку своей задачи в `docs/plan/tasks.md`.
2. Открой карточку задачи. Затем только перечисленные в ней входные документы и относящийся к изменению код. Не загружай весь каталог `docs`.
3. Статусы требований: CONFIRMED — принято владельцем; PROPOSED — рабочее предложение; OPEN — решения нет. Предложение не превращается в требование автоматически.
4. Если задача зависит от OPEN, подготовь варианты и конкретную рекомендацию; не принимай решение за владельца. Независимую работу продолжай.
5. У каждой механики один основной документ. Ссылки вместо повторов. Изменяя правило, обнови его источник и зависимые контракты/задачи.
6. Не меняй соседние подсистемы без необходимости. Несовместимость сначала отрази в контракте и решении.
7. Команды клиента не доверенные: экономика, время, владение, бой и видимость проверяются сервером. Секреты и реальные данные игроков в Git не коммитить.
8. Завершая задачу, укажи изменённые файлы, проверку критериев готовности и ограничения. Статус DONE ставится только при выполнении критериев.

## Ограничение контекста
Начальный пакет: эта инструкция + карточка + 1–3 входных файла. Дополнительное чтение — по ссылкам и конкретной необходимости. Не читать соседние карточки «на всякий случай». Если документ разросся примерно свыше 150 строк, выделить самостоятельную тему и обновить индекс. Не дробить каждый абзац в отдельный файл.

## Структура
`docs/gdd/` — поведение игры; `docs/tech/` — технические ограничения и контракты; `docs/plan/` — этапы и задачи; `docs/decisions/` — решения; `docs/templates/` — шаблоны. Кодовая структура и команды сборки будут определены после выбора стека. Не придумывать команды проверки до их появления.
